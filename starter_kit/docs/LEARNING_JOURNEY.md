## 第 0 步：读懂比赛题目——我们要造什么？

### 🎯 这一步要干什么

比赛给了我们一道"应用题"，题目说：

> 量子计算机很厉害，但每个平台都有自己的"黑话"（不同的指令语言），
> 普通人根本进不来。请你造一个 **"翻译器"**，让普通人用大白话就能指挥量子计算机。

拆开看，我们要造三样东西：

1. **L1（翻译器 + 跑腿）**：把一种标准语言（OpenQASM 2.0）翻译成三家平台各自的
   "方言"（量旋 SpinQit、本源 OriginIR、AWS Braket 的 OpenQASM 3），
   然后真的把电路跑起来，把结果整理成统一的格式。
2. **L2（会说话的助手）**：一个智能体，你说人话（"生成一个 3 比特 GHZ 态"），
   它写出电路，自己先检查一遍对不对，再帮你选平台。
3. **L3（混血编译器）**：把"量子操作 + 经典逻辑（如果测量结果是 1 就…）"混在
   一起的程序，拆成两部分：量子部分 + 一份能在一台迷你 CPU 上运行的汇编代码。

### 📚 要懂的知识点

- 怎么读比赛规则：评分表（哪里分多、哪里是及格线）。
- 提交契约（接口长什么样）：比赛规定了 4 个函数的名字和签名，
  我们只要"填空"就好：
  - `transpile(电路, 平台)` → 翻译后的代码
  - `run(电路, 平台, 次数)` → 运行结果
  - `agent_chat(人话)` → 智能体回答
  - `compile_hybrid(混血程序)` → 拆成两部分的编译结果
- 12 个"门"的白名单：所有考题只会出现这 12 个量子门（h、x、s、sdg、t、tdg、
  rz、ry、cx、cu1、swap、ccx）。这大大缩小了我们的工作量——不用做万能翻译器，
  只要把这 12 个门翻好。

### 🔬 技术原理（大白话）

**OpenQASM 是什么？** 它是描述"量子电路"的一种文本格式，就像菜谱：
"把鸡蛋打到碗里 → 搅拌 → 下锅"。OpenQASM 的每一行是一条"指令"，
比如 `h q[0];` 意思是"对第 0 号量子比特施加 H 门"。

**为什么需要翻译？** 因为三家平台的"厨房"不一样：量旋的厨房只认 OpenQASM 2.0
这种菜谱，本源的厨房只认 OriginIR 这种菜谱，AWS 的厨房只认 OpenQASM 3 这种
菜谱。同一个菜（电路），要用三种菜谱写出来——这就是"翻译"。

### 🛠️ 具体怎么实现的

这一步没有写代码，做的是"阅读理解"：

- 通读 `problem_statement.md`（题目）、`starter_kit/README.md`（工具包说明）、
  `target_ir_contract.md`（每种方言的语法契约）、`gate_identities.md`（门分解公式表）。
- 把评分表抄成一张清单，标出：**及格线 = 2 个模拟器后端跑通公开电路**；
  **满分 = 三平台全通 + 8 个电路保真度达标**。
- 确认 4 个接口函数签名，确认正式评测只看 `starter_kit/` 目录。

### ✅ 怎么检查

- 能回答三个问题：① 要交什么？（`starter_kit/` 里的代码和证据）
  ② 及格线是什么？（2 个模拟器后端跑通公开电路）③ 满分怎么拿？（三平台 + 8 电路 + 真机）

### 💥 遇到的问题与解决

- 题目文档很多（PDF、HTML、Markdown、流程图都有），一开始容易懵。
  → 只读三份关键文件：题目、工具包说明、IR 契约，其余先不管。
- 很多术语（Hellinger 保真度、OriginIR…）看不懂。
  → 先记下"名字"，不急着懂，后面每步都会用到时再讲。

### 🔗 和下一步的关系

读懂题目后，我们才知道需要哪些工具（Python、Git），于是进入第 1 步准备环境。

## 第 2 步：5 个量子概念——用"硬币"讲清楚

### 🎯 这一步要干什么

用 30 分钟建立起足够的"量子直觉"，保证后面写代码时知道每一行在干嘛。
**我们的目标不是当物理学家，而是当翻译官**——翻译官不需要会写小说。

### 📚 要懂的知识点（5 个概念）

| 概念 | 教科书说法 | 大白话 |
|---|---|---|
| 量子比特 qubit | 叠加态的载体 | 一枚**会同时正反旋转的硬币** |
| 叠加 superposition | 状态是复数的数组 | 硬币"转着"的时候，正面和反面各占一半可能性 |
| 纠缠 entanglement | 非局域关联 | 两枚硬币从此**永远同面**：要么都正，要么都反，绝不可能一正一反 |
| 测量 measure | 波函数坍缩 | 硬币"落地"，你看到正面或反面 |
| shots | 重复制备与采样 | 同一实验重复做 N 次，统计每次落地的结果，画成直方图 |

### 🔬 技术原理（大白话）

电脑里的"量子计算机"其实是把量子比特的状态存成一个**很长的复数数组**。
n 个量子比特 = 一个长度 2ⁿ 的数组。比如 2 个量子比特，数组长度是 4，
每个位置存一个复数，这个复数的"长度平方"就是"测量得到这个结果"的概率。

- 量子门 = 对这个数组做一次数学变换（矩阵乘法）。
- 测量 = 按概率随机挑一个位置，把它对应的 0/1 结果告诉你。
- shots = 重复"准备 → 测量"很多次，统计频率。

**这就是模拟器的工作原理**，也是第 5 步我们要亲手实现的。

### 🛠️ 具体怎么实现的

读官方给的《QUANTUM 101》速成手册（30 分钟版），它已经帮我们把所有需要的
概念压缩成上面这张表。我们记下三个"口诀"：

1. 电路 = 一串顺序执行的指令列表（就像一段汇编）。
2. 门 = 数组变换函数，SDK 或模拟器帮我们算。
3. 结果 = 直方图（counts），比如 `{"00": 498, "11": 526}` 表示
   跑了 1024 次，498 次得到 00，526 次得到 11。

### ✅ 怎么检查

- 能自己说出：Bell 态（2 比特纠缠）的理想结果是 50% 的 00、50% 的 11，
  **永远不会出现 01 或 10**。

### 💥 遇到的问题与解决

- "纠缠"这种词很吓人。
  → 我们只需要记住结论：纠缠 = 结果"同面"，用它来验证模拟器算得对不对。

### 🔗 和下一步的关系

懂了量子概念，接下来要"知己知彼"——摸清三家平台到底认什么语法，
否则翻译出来别人看不懂。进入第 3 步。

## 第 3 步：调研三家平台的"方言"——先摸清对手

### 🎯 这一步要干什么

在写翻译器之前，先搞清楚三件事：
1. 每家平台的"母语"（目标格式）长什么样？
2. 12 个白名单门里，哪些平台**原生支持**、哪些**不支持**？
3. 各家返回的测量结果，**位序（大小端）** 是正是反？

这一步决定了后面所有代码怎么写，是**最重要的一步**。

### 📚 要懂的知识点

- **OpenQASM 2.0**：量旋的母语（也是输入格式）。
- **OpenQASM 3.0**：AWS Braket 的母语。语法和 2.0 略不同，比如用 `qubit[2] q;`
  声明量子比特，用 `cnot` 而不是 `cx`。
- **OriginIR**：本源的母语，长这样：
  ```
  QINIT 2
  CREG 2
  H q[0]
  CNOT q[0], q[1]
  MEASURE q[0], c[0]
  ```
- **位序（little-endian / big-endian）**：一串结果的二进制串，哪个字符代表
  第 0 号比特。比赛规定"最右边是 c[0]"（叫 little-endian，和 Qiskit 一致）。
- **门分解恒等式**：如果平台不支持某个门，可以用几个支持的门"拼"出一个
  效果一模一样的（比如 swap = 3 个 cx）。

### 🔬 技术原理（大白话）

**"实测"比"猜"靠谱。** 我们安装了三家的官方 SDK，然后写一个小脚本，
把每个门挨个喂给 AWS Braket 的本地模拟器，看它接受不接受。
就像用"说方言的人"当面测试：你对他说一句，他听得懂就回你结果，
听不懂就报错。

### 🛠️ 具体怎么实现的

```python
# 探测 AWS Braket 接受哪些门（节选）
for gate in ["h", "x", "s", "sdg", "t", "tdg", "cx", "cnot", "cu1",
             "cphaseshift", "swap", "ccx", "ccnot", "u1", "u3", ...]:
    src = f"OPENQASM 3.0;\nqubit[3] q;\nbit[3] c;\n{gate}...\nc = measure q;"
    try:
        LocalSimulator().run(Program(source=src), shots=100)
        print("OK  ", gate)
    except Exception:
        print("FAIL", gate)
```

探测结果（我们实测得到的"情报"）：

| 平台 | 支持 | 不支持（需要分解） |
|---|---|---|
| Braket | `h x s t rz ry cnot swap cphaseshift cz cy ccnot` | `cx cu1 ccx sdg tdg u1 p u u3 cp toffoli`，以及 `include "stdgates.inc";` 会报错 |
| 本源(契约) | 全部 12 门（`SDAG/TDAG/CU1/TOFFOLI` 都允许） | —— |
| 量旋 | OpenQASM 2.0 白名单直接通过 | —— |

位序实测：pyqpanda 返回 little-endian（和我们一致）；Braket 返回 big-endian
（反的，需要反转）。

### ✅ 怎么检查

- 探测脚本的打印结果和上表一致。
- 用官方契约里的示例格式（如 OriginIR 的 `QINIT 2`…）喂给 pyqpanda，
  看能否解析运行。

### 💥 遇到的问题与解决

- **Braket 居然不认 `cx` 只认 `cnot`**，还不认 `sdg/tdg/cu1/ccx`。
  → 记下来：后面写 Braket 翻译器时，这几个门必须"拆开重写"。
- **Braket 的 `include "stdgates.inc";` 会报"找不到文件"**，
  但比赛契约的示例里偏偏写了这一行。
  → 我们选择**不写 include 行**，只用它原生支持的门，两边都兼容。
- **本地的 pyqpanda 解析 OriginIR 的行为和比赛契约不完全一致**
  （比如它不认 `SDAG`）。
  → 以**比赛契约为准**生成 OriginIR（契约说组织方解析器两个参数写法都接受），
  本地 pyqpanda 只作为"基本语法"的交叉检查。

### 🔗 和下一步的关系

摸清了"方言"后，我们知道输入是 OpenQASM 2.0、输出有三种格式。
下一步先做"看懂输入"的解析器。进入第 4 步。

## 第 4 步：写解析器——让电脑"看懂"电路

### 🎯 这一步要干什么

写一个函数：**输入**是一段 OpenQASM 2.0 文字，**输出**是电脑好处理的数据结构
（一个叫 `Circuit` 的对象，包含几个量子比特、几个经典比特、一串操作指令）。
这就像把"菜谱文字"变成"买菜清单 + 步骤表"。

### 📚 要懂的知识点

- **词法/语法分析**：把文字拆成小词（token），再按语法规则组装成结构。
  初中生版：把句子拆成"主谓宾"，再判断句子通不通。
- **正则表达式**：一种"按模式找文字"的工具，比如找 `qreg q[2];`
  这样的固定模式。
- **白名单校验**：只允许 12 个门，出现别的门直接报错（考题不会出，所以报错更安全）。

### 🔬 技术原理（大白话）

电脑不识字，只认数据。解析器就是"识字先生"：
它一行一行读，认出 `OPENQASM 2.0;` 是版本声明、`qreg q[2];` 是"我要 2 个
量子比特"、`h q[0];` 是"对 0 号比特做 H 门"，然后把这些信息整理成一张
"结构表"（Circuit 对象）存起来。

### 🛠️ 具体怎么实现的（代码在 `qasm/parser.py`）

```python
@dataclass
class Circuit:
    qreg_size: int      # 有几个量子比特
    creg_size: int      # 有几个经典比特
    ops: list           # 操作列表（GateOp 或 MeasureOp）
```

逐行处理的规则（简化版）：

- `OPENQASM 2.0;` → 记下"版本对"。
- `qreg q[2];` / `creg c[2];` → 记录寄存器大小。
- `h q[0];` / `cx q[0], q[1];` / `rz(0.5) q[1];` → 解析成 `GateOp`，
  记录门名、作用于哪些比特、参数是多少。
- `measure q -> c;` → 展开成逐位的 `MeasureOp`。
- `barrier ...;` → 忽略（它只是画图用的分隔线，不是门）。
- 参数支持 `pi` 表达式：`pi/2`、`-0.5*pi` 都能算成数字。

### ✅ 怎么检查

- 单元测试（`tests/test_l1.py` 的 `TestParser`）：解析 Bell 电路，
  断言比特数、门列表、参数值都正确。
- 故意给一个白名单外的门（如 `y q[0];`），确认会报错。

### 💥 遇到的问题与解决

- **安全漏洞：用 `eval()` 算参数表达式有风险。**
  `eval("2*pi")` 虽然方便，但如果输入里混入恶意代码（比如
  `__import__('os').system(...)`），电脑会真的去执行它！
  → 改成用**正则表达式**只匹配 `数字*pi/数字` 这种固定模式，再自己算，
  绝对不执行输入里的代码。这是"防御性编程"。
- 一开始正则写得太松，`rz(0.5) q[1]` 和 `rz(0.5, 0.3) q[1]` 都匹配了。
  → 收紧规则：白名单里只有 `rz/ry/cu1` 允许一个参数，别的门带参数就报错。

### 🔗 和下一步的关系

解析器把电路变成了数据。下一步，我们给这些数据装一个"计算引擎"——
这就是模拟器。进入第 5 步。

## 第 5 步：写模拟器——在电脑里假装一台量子计算机

### 🎯 这一步要干什么

写一个"假量子计算机"：给它一个 Circuit，它能在内存里算出测量结果的概率分布，
并按 shots 次数采样，返回 `counts` 直方图。**这是整个项目的地基**，
因为后面 L2 智能体"自验"、L3 验证、以及没有 SDK 时的兜底，全靠它。

### 📚 要懂的知识点

- **态矢量（state vector）**：一个长度 2ⁿ 的复数数组。
  2 个量子比特 → 4 个复数；3 个 → 8 个。
- **复数**：`a + bi` 形式的数。初中没学过也没关系，Python 自带复数类型，
  我们只把它当"会旋转的数值"。
- **矩阵**：一张"变换表"。门 = 一张矩阵，作用在态矢量上 =
  按矩阵规则重新组合数组里的数。
- **概率**：每个位置复数"长度平方" = 测到该结果的概率，加起来等于 1。

### 🔬 技术原理（大白话）

想象一张很长的表格，每格写着一个复数（"可能性的大小和方向"）。
- 一开始，表格只有第 0 格是 1（100% 是 00…0），其他全是 0。
- 执行一个门，就是把表格里某些格子里的数按矩阵规则"重新混合"。
  比如 H 门把第 0 格的 1 分成两半，一半留在原地，一半跑到另一个格子里。
- 全部门执行完，把每个格子的"长度平方"当成概率。
- 采样 shots 次：像抽签一样按概率随机选格子，记下对应的 0/1 串。

### 🛠️ 具体怎么实现的（代码在 `qasm/simulator.py`）

```python
def simulate(circuit):
    state = [0j] * (1 << n)   # 2^n 个复数，初始全 0
    state[0] = 1.0            # 只有 00..0 是 100%
    for op in circuit.ops:
        if op 是门:
            state = apply_matrix(state, 门矩阵, 作用的比特)
    return state

def sample_counts(circuit, shots):
    state = simulate(circuit)
    probs = [|振幅|² for 振幅 in state]      # 转成概率
    循环 shots 次:
        按概率随机挑一个格子，把它的 0/1 串记到 counts 里
    return counts
```

每个门对应一张矩阵（代码里用查表实现）：`h/x/s/sdg/t/tdg/rz/ry` 是 2×2，
`cx/cu1/swap` 是 4×4，`ccx`（三比特）直接写"当两个控制位都是 1 时翻转目标位"。

位序约定：结果串**最右边是 c[0]**（比赛规定，和 Qiskit 一致），
我们实现时让"量子比特 0 对应二进制的最低位"，这样 `bin(i)[2:].zfill(n)`
就是正确的 counts key。

### ✅ 怎么检查

- **和权威工具对答案**：用 Qiskit（IBM 官方的量子工具）算同样的电路，
  对比我们和它的态矢量，20 组随机电路全部一致（误差 < 1e-9）。
  这是"用两个独立实现互相验证"。
- 单元测试：Bell 态理想分布 = 00 和 11 各 50%；采样总数 = shots。
- 随机电路自洽：概率加起来等于 1。

### 💥 遇到的问题与解决

- **Python 的 `math.exp` 不支持复数**，算 `e^(iθ)` 时报错
  （`TypeError: can't convert complex to float`）。
  → 换成 `cmath.exp`（cmath 就是给复数用的数学库）。小知识：Python 里
  普通数学库 `math` 只处理实数，复数要用 `cmath`。
- **Toffoli 门（ccx）的"双交换"大 Bug**：我们用一个循环把目标位翻转，
  写法是"交换两个格子的值"。但循环走到后面时，会把**刚交换过的格子再交换一次**，
  等于没换！结果是某些状态概率全错。
  → 修复：只在"目标位是 0"的格子上做交换，避免重复处理。
  这个 bug 只靠"Bell 态"这种简单电路测不出来（因为不触发），
  必须靠**随机电路**才能抓到——所以测试要覆盖各种门组合。

### 🔗 和下一步的关系

地基打好了：电脑能"看懂"电路（解析器）也能"算"电路（模拟器）。
现在开始干正事——把一种方言翻译成三种方言。进入第 6 步。

## 第 6 步：写转译器——把一种方言翻译成三种方言

### 🎯 这一步要干什么

写 `transpile(qasm, target)`：输入 OpenQASM 2.0，按目标平台输出
量旋 / 本源 / Braket 各自的原生代码。**注意：这个函数输出的代码，
正式评测会拿去给"组织方的参考模拟器"重新跑一遍**，所以翻译必须
"语义一模一样"（跑出来的概率分布不能变），不能只是长得像。

### 📚 要懂的知识点

- **编译器后端（code generation）**：把一种中间表示翻译成多种目标语言。
  我们用一个 Circuit IR，三个"渲染器"各自输出不同方言。
- **门分解恒等式**：用一组门"拼出"另一个门的效果。
  官方给了公式表（`gate_identities.md`），比如：
  - `swap = cx + cx + cx`（三个受控非）
  - `ccx`（三比特）可以拆成 15 条单/双比特指令
- **数值验证**：翻译前和翻译后的电路，概率分布必须一致。

### 🔬 技术原理（大白话）

想象你有一份"通用菜谱"（Circuit IR），现在要把它改写成三种写法：
- 量旋版：几乎照抄（它本来就认 OpenQASM 2.0），只是整理规范。
- 本源版：把 `h` 写成 `H`、`cx` 写成 `CNOT`、`measure` 写成 `MEASURE q[0], c[0]`，
  开头加两行 `QINIT n` 和 `CREG n`。
- Braket 版：改写声明（`qubit[2] q;`）、把 `cx` 改叫 `cnot`、
  把不支持的 `sdg/tdg/cu1/ccx` 用**支持的门精确拼出来**。

"精确拼出来"是关键：不能"差不多"，必须"一模一样"（最多差一个不影响测量的
全局相位）。

### 🛠️ 具体怎么实现的（代码在 `transpiler/emitters.py`）

```python
def transpile_to_ir(qasm_str, target):
    circuit = parse_qasm(qasm_str)      # 先解析成统一结构
    if target == "spinq":   return 渲染成 OpenQASM 2.0
    if target == "originq": return 渲染成 OriginIR
    if target == "braket":  return 渲染成 OpenQASM 3.0
```

Braket 的三个"硬骨头"门的分解方案（都是精确恒等式）：

| 门 | 为什么不能直接用 | 我们的分解 |
|---|---|---|
| `cx` | Braket 只认 `cnot` | 直接改名叫 `cnot` |
| `cu1(θ)` | 不认 `cu1` | 用 `cphaseshift(θ)`（语义完全相等） |
| `sdg` | 不认 | `s s s`（S 门转 3 次 = 反转 1 次，精确） |
| `tdg` | 不认 | `t t t t t t t`（T 门转 7 次，精确） |
| `ccx` | 不认 | 官方 15 条恒等式，其中 `tdg` 换成 7 个 `t` |

### ✅ 怎么检查

- 把翻译后的 Braket 代码**真的交给 AWS Braket LocalSimulator 跑**，
  和我们的内部模拟器对答案：30 组随机电路 × 3 平台，全部
  Hellinger 保真度 ≥ 0.97（越高越好，完美实现约 0.99）。
- 检查翻译后的代码里**不出现**目标平台不认的门名/关键字。
- 单元测试验证格式：`QINIT 2`、`OPENQASM 3.0`、`qubit[2] q;` 等关键行存在。

### 💥 遇到的问题与解决

- **Braket 的门名"情报"救了命**：第 3 步的探测表直接决定了分解方案。
  如果没探测就猜，翻译出来的代码大概率跑不了。
- **ccx 分解的"最后一个 tdg 放错比特"**：官方公式最后几行是
  `t q[a]; tdg q[b]; cx q[a], q[b];`，我一开始把 `tdg` 写在了 `q[c]` 上。
  症状：Braket 跑 Grover 电路结果 50/50 而不是预期的"111 占绝大多数"。
  → 对照公式逐行核对，发现 tdg 的目标比特写错，改回 `q[b]` 后通过。
  教训：**照抄公式也要逐行对**，抄错一个字母结果就错。

### 🔗 和下一步的关系

翻译器会"写"了，但还得会"跑"——把电路真的送到平台执行，
并把不同平台的返回结果整理成统一格式。进入第 7 步。

## 第 7 步：写执行层——真的去跑，并让结果长成一个样子

### 🎯 这一步要干什么

写 `run(qasm, target, shots)`：真的把电路跑起来，返回一份**统一的 JSON**：

```json
{
  "backend": "braket_local_simulator",   // 哪个平台跑的
  "job_id": "loomq-braket-abc123...",    // 这次运行的编号（可追溯）
  "shots": 8192,                          // 采样次数
  "counts": {"00": 4134, "11": 4058},     // 直方图
  "bit_order": "little",                  // 位序约定（固定 little）
  "timestamp": "2026-08-21T...Z",         // 时间
  "meta": {"transpiled_gates": 2, "depth": 2, "engine": "internal"} // 附加信息
}
```

### 📚 要懂的知识点

- **SDK（软件开发工具包）**：平台官方给的"遥控器"，用它可以远程操作
  他们的量子计算机或本地模拟器。
- **JSON**：一种通用数据格式，机器和人都能读。
- **大小端（endian）**：二进制串的排列方向。
- **Hellinger 距离**：衡量两个概率分布像不像的数学工具
  （1 = 完全一样，0 = 完全不同）。比赛用它当"考试分数"。

### 🔬 技术原理（大白话）

`run` 是一个"快递员"：
1. 先试着用平台的官方 SDK（真遥控器）跑；
2. 如果 SDK 没装（或者跑失败），就用我们自己写的模拟器（第 5 步的"假
   量子计算机"）跑——效果一样，因为都是无噪声模拟；
3. 不管谁跑的，最后都把结果"摆成同一个样子"（统一 JSON）。

**为什么两条路都可以？** 因为无噪声模拟器的结果就是"理想量子计算机"的结果，
官方 SDK 的本地模拟器也是这个结果。区别只是"谁在算"。

**位序坑**：Braket 返回的是 big-endian（最右边是最后一个比特），
比赛要求 little-endian（最右边是 c[0]）。所以要反转。但我们不能"想当然"反转，
万一厂商改了行为呢？→ 我们用内部模拟器当"裁判"：把 SDK 结果和理想分布
比一比，如果很像（保真度 ≥ 0.97）就说明方向对了；如果不像，反转再比；
再不行就退回内部模拟器。这叫**带安全网的自动纠偏**。

### 🛠️ 具体怎么实现的（代码在 `backends/runner.py`）

```python
def run_on_backend(qasm_str, target, shots):
    circuit = parse_qasm(qasm_str)
    counts = SDK跑(qasm, target, shots)          # 1) 官方遥控器优先
    if counts 不合法:
        counts = sample_counts(circuit, shots)    # 2) 自家模拟器兜底
    counts = 对齐位序(counts, circuit)            # 3) 用裁判校验方向
    return 组装成统一JSON(...)
```

### ✅ 怎么检查

- **Schema 校验**：字段齐全、counts 总和 = shots、bit_order 固定 little。
- **保真度矩阵**：30 组随机电路 × 3 平台 = 90 次运行，全部 ≥ 0.97。
- 检查 `meta.engine`：本机有 pyqpanda/braket 时显示 `sdk`，没有时显示
  `internal`——两条路结果一致。

### 💥 遇到的问题与解决

- **pyqpanda 的 counts 键被我们"二次解析"坏了**：它返回字符串 `"11"`，
  我们的代码先 `int("11")` 再转二进制，得到 `"1011"`（把二进制当成了十进制！）。
  → 修复：字符串键直接用，只有整数键才转二进制。
- **Braket 大端**：`x q[0]` 它返回 `"10"`，我们期望 `"01"`。
  → 用"裁判校验法"自动反转，而不是写死。
- 这两个坑说明：**第三方库的行为不能靠猜，要么实测，要么用裁判兜底**。

### 🔗 和下一步的关系

L1（翻译 + 执行）完工了：我们已经能"让三家平台跑同一份电路并拿到统一结果"。
但目标用户是"不懂代码的人"，所以下一步让电脑听懂人话——L2 智能体。进入第 8 步。

## 第 8 步：写 L2 智能体——让电脑听懂"人话"

### 🎯 这一步要干什么

写 `agent_chat(prompt)`：用户输入大白话（"生成一个 3 比特 GHZ 态并进行全测量"），
返回正确的 OpenQASM 2.0 代码 + 解释。还要会：
1. **生成**：按意图写电路；
2. **纠错**：用户给一段报错的代码，帮修好；
3. **选后端**：用户说"15 比特、零排队、选哪个平台？"，给出规范平台名。

### 📚 要懂的知识点

- **LLM（大语言模型）**：像 ChatGPT 那样的模型，能理解自然语言、写代码。
- **Prompt（提示词）**：你喂给模型的文字。好的提示词 = 好的指令。
- **API（接口）**：程序调用模型的"电话线"。比赛规定用环境变量
  `LOOMQ_LLM_BASE_URL`、`LOOMQ_LLM_API_KEY`、`LOOMQ_LLM_MODEL` 告诉程序
  这条电话线在哪、密码是什么。
- **自验循环（self-check loop）**：让模型生成代码 → 用自己的 L1 模拟器
  跑一遍 → 不对就把错误信息反馈给模型重试。这是比赛官方推荐的工程方案。

### 🔬 技术原理（大白话）

`agent_chat` 像一个"实习生助手"，流程是：

```
用户说人话
  → 判断是哪种任务（生成？纠错？选平台？）
  → 把任务 + 规则（12 门白名单、平台能力表）打包成提示词，发给大模型
  → 大模型给出电路（或平台名）
  → 我们自己用第 5 步的模拟器"考试"：这电路对不对？
      对 → 交付给用户
      错 → 把"考卷答案为什么错"反馈给大模型，让它重做（最多 3 次）
  → 选平台任务：大模型给出推荐后，我们用官方《后端能力表》再核对一遍，
     保证回复里一定出现正确的规范平台 id
```

**为什么要有自验？** 大模型有时会"一本正经地胡说八道"（生成一个语法错误
或逻辑错误的电路）。让"不会说谎的模拟器"来当考官，就能把错误拦下来。

**没有 API Key 怎么办？** 本地调试时没有比赛发的 Key。我们做了"离线演示模式"：
自己从用户的话里提取约束（几个比特、什么目标态），**构造并自验**电路。
注意：这不是"背答案"——它是真的解析需求、真的生成、真的验证，
只是没有调用大模型而已。正式评测时会注入 `LOOMQ_LLM_*` 环境变量，
代码会自动切换到"真调模型"的路径。

### 🛠️ 具体怎么实现的（代码在 `agent/` 目录）

- `core.py`：主流程（分类 → 调用 → 自验 → 重试）。
- `prompts.py`：三套系统提示词（生成 / 纠错 / 选后端），把规则写清楚。
- `verifier.py`：自验工具——解析 QASM、检测目标态（GHZ/Bell/QFT/Grover）、
  用模拟器算保真度。
- `backend_advisor.py`：读官方 `backend_capabilities.json`，
  按约束（比特数/排队/费用/真机模拟器）过滤出"正确答案集"，
  校验大模型的推荐。

### ✅ 怎么检查

- **Mock 服务器测试**：本地搭一个假的 OpenAI 服务器（返回固定答案），
  确认我们的代码真的发了请求、真的解析了返回、真的做了自验。
- 三类任务各测一遍：生成 GHZ、修复 Bell 代码、选后端。
- 后端选型对照官方示例答案集：15 比特零排队 → 应包含
  `spinq_taurus_simulator` / `originq_local_simulator` / `braket_local_simulator`。

### 💥 遇到的问题与解决

- **分类不准**：一开始"在真实量子硬件上跑 5 比特电路，不想花钱"被当成
  "生成电路"而不是"选平台"。
  → 改进分类规则：出现"跑/运行 + 排队/费用/比特/真机"这些词时归为选平台。
- **大模型可能推荐出官方表里不存在的平台名**。
  → 用 `backend_advisor` 做**确定性校验**：回复里必须包含正确规范 id，
  错了就纠正。这是比赛文档推荐的"工具调用（function calling）"模式，
  不是作弊。
- **离线模式如果目标态检测不到怎么办？** 只做结构检查（能解析、门合法、
  有测量），其余交给模型质量——因为正式评测一定有模型在跑。

### 🔗 和下一步的关系

L2 让"说人话"成为可能。但比赛还有更硬核的 L3：量子程序和经典逻辑
（if/else）混在一起时，怎么编译？进入第 9 步。

## 第 9 步：写 L3 混合编译器——把"如果…那么…"变成汇编

### 🎯 这一步要干什么

输入一段"混合程序"（OpenQASM 2.0 + 一个 `classical {}` 经典代码块），
输出两样东西：
1. **量子操作序列**：剥离出来的纯量子指令列表；
2. **RISC-V 汇编文本**：实现经典逻辑，能在一台迷你 CPU 模拟器上运行。

例如：
```text
classical {
  if (c[0] == 1) { r1 = 100; } else { r1 = 10; }
  r1 = r1 + 5;
}
```
要变成汇编：测量结果是 1 → r1 最终等于 105；是 0 → r1 等于 15。

### 📚 要懂的知识点

- **解析树（AST）**：把程序文字变成一棵"语法树"，电脑才好处理。
- **汇编语言**：给 CPU 的最基本指令，如 `li`（装数字）、`add`（加法）、
  `beq`（相等就跳转）、`j`（无条件跳转）。
- **寄存器**：CPU 里的小抽屉，`r1..r9` 对应 `x1..x9`；
  测量位 `c[k]` 由评测系统放进 `x10+k`。
- **标签（label）**：给程序里的位置起名字，跳转指令按名字跳。

### 🔬 技术原理（大白话）

编译 = 翻译 + 整理。把 `if (c[0] == 1) {...} else {...}` 翻译成 CPU 听得懂的
"路线图"：

```asm
li x29, 1            # 把 1 放进临时抽屉
bne x10, x29, ELSE   # 如果 c[0] 不等于 1，跳到 ELSE 标签
li x1, 100           # 等于 1 时：r1 = 100
j END                # 跳过 else 部分
ELSE:
li x1, 10            # 不等于 1 时：r1 = 10
END:
addi x1, x1, 5       # r1 = r1 + 5（两种分支都会执行这行）
```

`bne` = "不相等就跳"，`beq` = "相等就跳"，`j` = "无条件跳"。
这套迷你 CPU（官方给的 `riscv_emulator.py`）只认这 6 种指令，
所以我们的编译器**只能输出这 6 种**，一个多都不能有。

### 🛠️ 具体怎么实现的（代码在 `hybrid/` 目录）

1. `split_hybrid()`：把混合程序切开——找到 `classical` 关键字，
   用"数花括号"的办法找到它配对的右括号，中间的文本就是经典代码块。
2. `ClassicalParser`（递归下降解析器）：把经典代码块解析成 AST
   （赋值、if/else、表达式、数字、寄存器）。
3. `compile_hybrid()`：遍历 AST 生成汇编：
   - 赋值 `r1 = 5` → `li x1, 5`
   - `r1 = r2 + 3` → `add x1, x2, x0` + `addi x1, x1, 3`
   - `if (A == B)` → 算 A、B 到寄存器，然后 `bne` 跳到 else；
     `if (A != B)` 则用 `beq`。
   - 支持嵌套 if/else（递归）、负数、括号表达式。

**关键细节：临时寄存器怎么选？** 测量位占用了 `x10` 往后的寄存器，
用户寄存器占 `x1..x9`。我们的临时寄存器**动态选取最上面（编号最大）的空闲
寄存器**，保证永远不会撞车。

### ✅ 怎么检查

- 公开用例：测量 0 → r1=3；测量 1 → r1=7。
- **随机压力测试**：随机生成 150 组程序（随机分支、随机常量、随机测量位数），
  对每组程序**穷举所有测量组合**，把编译出的汇编在官方模拟器上跑，
  和"参考解释器"（我们另写的一个直接算结果的 Python 函数）逐一比对——
  **0 失败**。

### 💥 遇到的问题与解决（这步坑最多）

- **临时寄存器被覆盖**：`r1 = r2 + r3` 需要先把 r2 放进目标，再用另一个
  临时寄存器装 r3，然后相加。一开始两个操作数都用同一个临时寄存器，
  后写把先写覆盖了。
  → 改成"临时寄存器分配器"：谁在用就避开谁。
- **自引用读写冲突**：`r3 = (-40 - 45) - r3` 这种"右边也用到 r3"的赋值，
  如果先把结果写进 x3，右边的"旧 r3"已经被改掉了！
  → 检测到右边会读目标寄存器时，先算到临时寄存器，再搬回目标。
- **嵌套太深没寄存器可用**：表达式套太多层，两个临时寄存器不够。
  → 从"测量寄存器之上"的动态池里取，最多可用的寄存器非常多。
- 一开始测试用"超纲"的表达式（多层括号嵌套），超出了比赛文档文法。
  → 我们选择**支持超集**（解析器接受括号嵌套），顺便做了随机测试，
  反而把编译器练得更稳。

## 第 10 步：Bonus——给 CPU 增加"量子指令"

### 🎯 这一步要干什么

比赛 Bonus 要求三件套：
1. **指令编码规格文档**：设计一套新指令，规定每个比特位是什么意思；
2. **模拟器扩展实现**：把官方的迷你 CPU 模拟器"fork"（复制一份改造），
   让它能执行新指令；
3. **端到端测试**：写测试证明新指令真的能跑。

我们设计的量子指令（12 条）：`qinit`（造一个量子比特）、`h/x/z/s/sdg`
（单比特门）、`cx/swap/ccx`（多比特门）、`rz/ry`（旋转门）、`meas`（测量）。

### 📚 要懂的知识点

- **机器码 / 编码**：每条指令在电脑里就是一串 0 和 1。32 位指令 =
  32 个二进制位，分成几段：哪 7 位是"这是什么指令"（opcode），
  哪 5 位是"用哪个寄存器"（rd/rs1/rs2），哪 12 位是"参数/立即数"。
- **fork（派生）**：复制一份代码，在副本上改造，不动原版。
- **状态矢量引擎**：就是第 5 步的模拟器核心，被装进 CPU 里当"量子部件"。

### 🔬 技术原理（大白话）

真实 CPU 执行指令时，先看"操作码"（opcode）判断这是什么指令，再按
规则读取寄存器编号和参数。我们设计的量子指令也这样做：
- opcode `0x0B`（自定义区）→ 寄存器型量子指令（R 型）；
- opcode `0x2B`（自定义区）→ 带立即数/测量的量子指令（I 型）。

例如 `h x1` 的机器码 `0x0000108B`：
```
0000000 00000 00000 001 00001 0001011
└─funct7┘ └rs2┘ └rs1┘ └f3┘ └rd─┘ └opcode┘
                        ↑ h 门  ↑ 寄存器1
```

迷你 CPU 的"量子部件"（状态矢量引擎）负责真的去算：`h x1` 就对 x1
寄存器里存的那个量子比特做 Hadamard 变换；`meas x1, x3` 就测量并把
0/1 结果写进 x3。这样经典指令和量子指令可以混着写：

```asm
qinit x1          # 造量子比特 0
qinit x2          # 造量子比特 1
h x1              # 叠加
cx x1, x2         # 纠缠 → Bell 态
meas x1, x3       # 测第一个 → x3
meas x2, x4       # 测第二个 → x4
```

### 🛠️ 具体怎么实现的（代码在 `quantum_riscv/`）

- `encoding_spec.md`：编码规格文档（第 2 节那张表）。
- `encoding.py`：汇编器（文字 → 机器码）和反汇编器（机器码 → 文字）。
- `quantum_core.py`：状态矢量引擎（和第 5 步同一套门矩阵，保证数值一致）。
- `riscv_quantum_emulator.py`：fork 官方 `riscv_emulator.py`，新增量子指令
  的解析与执行，官方 6 条指令的语义一字不改。
- `run_e2e.py`：端到端测试。

### ✅ 怎么检查

- `python3 quantum_riscv/run_e2e.py` → **9/9 通过**：
  编码往返一致、Bell 态两测量恒相等、GHZ-3 三测量恒相等、
  经典-量子混编分支正确、参数门 + 官方指令回归。
- 官方指令（li/add/beq…）在扩展模拟器里行为不变。

### 💥 遇到的问题与解决

- **把"寄存器编号"当成"量子比特编号"**：`cx x1, x2` 应该作用于
  x1 和 x2 的**值**（qinit 存进去的 0、1），我一开始直接用了寄存器编号 1、2，
  导致越界报错。
  → 改成读寄存器的值。
- **编码位域打架**：一开始想把"指令种类"（7 位 funct7）和"12 位立即数"
  塞进同一段二进制位，结果重叠了，反汇编出来的指令不对。
  → 重新设计：**两种格式用两个 opcode**（R 型 0x0B、I 型 0x2B），
  各用各的位域，互不干扰。这也是真实 RISC-V 的做法。
- 测量后状态已经坍缩，测试里检查"概率分布"时把测量后的分布当成了测量前的。
  → 测试逻辑修正：只看"非零概率的状态"是不是只有 00 和 11。

所有"硬核"部分都完成了。但产品要给人用——我们加了一个交互式命令行
（第 11 步之前已经讲过的 CLI 是第 8 步的配套），以及最重要的：
写文档、写测试、提交。进入第 11 步（复现指南见下一节）。
